# ADR-0004: Artifact Staging and Atomic Publish Spike

- Status: Proposed for bounded spike review
- Date: 2026-08-16
- Task: M1-APP-003
- Milestone: M1
- Owner: APP/root
- Reviewer: QA/artifact-reviewer

## Context

M1-APP-001 fixed the desired Job/JobEvent behavior, and M1-APP-002 accepted local
SQLite single-writer, transaction migration, and restart scanning evidence. The current
application still writes through its v1 image/video paths and does not have a production
JobStore, artifact publisher, application facade, or recovery worker.

Phase 1 requires worker output to remain job-scoped and invisible until size/hash
verification succeeds. A crash on either side of final publication must produce a
deterministic reconciliation state rather than an automatic retry or overwrite.

## Decision Under Test

On the current Windows target, test a same-volume publisher with these steps:

1. Resolve and contain staging, intent, and final paths before any filesystem write,
   then write only to `.staging/<job_id>/<artifact_id>.part`, flushing chunks and
   calling `os.fsync()` before declaring the staged file ready.
2. Persist a compact publish intent containing the staging/final paths, size, and SHA-256.
3. Verify the staged bytes, reject any existing final path, then use same-volume
   `os.rename()` so the final name appears only after the complete file is ready.
4. Persist a receipt after rename. If the process exits after rename but before receipt,
   restart scanning verifies the final bytes and reports `receipt_required`; it never
   republishes automatically.
5. If the process exits before rename, scanning reports `staging_orphan`; cleanup is an
   explicit, idempotent action and never touches an existing final artifact.

All experiment files live under `TemporaryDirectory`. The harness does not read or
overwrite user files and does not connect to Electron, renderer, FastAPI, current image
or video services, or a production registry.

## Acceptance and Stop Conditions

Accept only if a partial `.part` never appears at the final path, hash/size mismatch
blocks publication, an existing final remains byte-identical, crash-before and
crash-after states are distinct, reconciliation never republishes, and cleanup/receipt
recovery is idempotent. Stop on any partial final visibility, overwrite, ambiguous state,
silent integrity mismatch, or test path outside its temporary root.

## Evidence Boundary

Passing tests are local E2 evidence for Windows, the recorded Python/filesystem, and
same-volume rename behavior. Python file `fsync` does not prove parent-directory metadata
durability under sudden power loss on Windows. Cross-volume moves, network filesystems,
antivirus interference, packaged Python 3.12, production userData, real large media,
and external-machine recovery remain unknown and require separate evidence.

## Rollback

Delete this ADR, `docs/evidence/M1/M1-APP-003/`, and the two artifact spike files.
Temporary directories remove all generated bytes. No production artifact, database,
user file, release object, immutable asset, or channel pointer requires restoration.
